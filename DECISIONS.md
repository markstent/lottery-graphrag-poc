| D-012 | 2026-10-18 | PyYAML is added as the ontology source format. | The ontology is a nested, multilingual document that is edited by hand; YAML keeps it readable and is the single source for concepts and bindings. | Ontology, dependencies |
| D-013 | 2026-10-18 | Channel codes stay shared across markets while every other taxonomy is market-local. | Channels are genuinely common across the four operators, whereas families, categories, mechanics, incident types, support categories and segments are what each source system names for itself. | Data, ontology, graph |
| D-014 | 2026-10-19 | Planted ids continue the table sequences and carry no scenario marker. | Retrieval must not be able to infer a plant from an identifier; scenario membership lives in the truth ledger only. | Scenarios, data |
| D-015 | 2026-10-19 | KPIs are derived after planting; injectors never edit `kpi_daily`. | Derived KPIs stay consistent with the rows they summarise, so no aggregate can contradict its source. | Scenarios, data |
| D-016 | 2026-10-19 | Scenario targets are drawn from the scenario seed among eligible candidates. | Different scenario seeds then plant different targets, and the same seed reproduces the same plant. | Scenarios, evaluation |
| D-017 | 2026-10-19 | Pipeline B's allow-list excludes exactly the ontology relationship types, and the per-question fraud profile is removed. | B is C minus the ontology, which isolates the value of the ontology; question-specific profiles would bias the comparison. | Retrieval, experiment |
| D-018 | 2026-10-19 | Every label the ranking treats as structured resolves to an authoritative source table. | Numerical and factual claims must come from the source layer, so ranked structured evidence needs a source record to cite. | Retrieval, provenance |
| D-019 | 2026-10-19 | `CONCEPT_PROGRESSIVE_JACKPOT` stays in the ontology without a binding. | A progressive jackpot is a game attribute (`jackpot_type_code`), not a market mechanic code, so no local code denotes it; the concept stays for vocabulary. | Ontology |
| D-020 | 2026-10-19 | Shared distribution shapes live in `app/datasets/distributions.py`; shape numbers specific to one table or one scenario may stay in their module when named and commented. | One place for the shapes several generators share, without moving every local number away from the code it shapes. | Data, scenarios |
| D-021 | 2026-10-19 | fastembed is the runtime for the sparse BM25 model (`Qdrant/bm25`) and the cross-encoder reranker (`BAAI/bge-reranker-v2-m3`). | One library, locked at 0.9.0 in `uv.lock`, runs both models locally on CPU with no service to operate, and the reranker is multilingual like the dense model. | Retrieval, dependencies |
| D-022 | 2026-10-19 | Hybrid retrieval fuses a dense and a sparse top-k on the client by reciprocal rank fusion with k=60, ties ordered by fused score, then dense rank, then id; this replaces Qdrant's server-side fusion. | Qdrant's tie-breaks are not reproducible, while client-side fusion gives the in-memory and Qdrant stores the same order by construction. | Retrieval, experiment |
| D-023 | 2026-10-19 | Every pipeline answers from one total context token budget and one evidence-slot cap, with no reserved slots per channel. | Equal context for A, B and C means any difference in answers comes from what each pipeline retrieved, not from how much it could show. | Retrieval, experiment |
| D-024 | 2026-10-19 | Answers use structured prompt v2 (`PROMPT_VERSION` 2.0.0): one JSON object with a verdict and a cited answer, parsed into checked `[n]` citations. | A verdict and parsed citations can be scored deterministically, and a citation to a block the model was never shown is dropped. | Retrieval, model layer |
| D-025 | 2026-10-19 | One shared judge (the reranker) selects context across the structured and document channels in every pipeline; the graph composite score ranks candidates only; a node is judged and shown on exactly A's record block for the same row; every pipeline hands the generator one list, its selection in judge order, with one citation builder and no B- or C-only prompt extra. | The same fact then gets the same text, judge and prompt block in A, B and C, and the same selected evidence gives the same prompt string, so the graph is measured on what it finds, not on how it is presented; a controller ruling from the first live run and the final review, open to the owner at CP1 part 2. | Retrieval, experiment |
| D-026 | 2026-10-19 | Document nodes are never traversal targets or structured candidates; documents reach every pipeline through the document channel. `GraphRagSettings.excluded_labels` is fixed at `("Document",)` with no environment variable and is recorded with every benchmark run. | Documents stay in the vector layer as the augmentation principle requires, and a document can no longer take two slots or a structured node's place; a controller ruling from the first live run, open to the owner at CP1 part 2. | Retrieval, graph |
| D-027 | 2026-10-19 | When no entity resolves, the fallback seed is the graph node of the top record hit in the shared vector layer; no record hit means no seed. | The seed is then a real, traversable record found with A's own models, and a seed is never invented; a controller ruling from the first live run, open to the owner at CP1 part 2. | Retrieval, graph |
| D-028 | 2026-10-19 | The judge and the model only ever see text pipeline A could have indexed: every table a structured node maps to has a record block (record serialiser 2.1.0 adds support cases, experiments, markets, platforms and channels), and a node whose row has no block is `<Label> <id>` only; authoritative columns stay on the node's evidence for citations and the UI. `RECORD_SERIALISER_VERSION` is stamped into `vector-index.json`; every lab (API, benchmark runner, trace CLI) refuses an index built by another version, and the reproducibility record takes the version from the manifest of the index in use. | Spec 5.4 gives A record blocks for equal warehouse access, so a humanised sentence of columns A cannot retrieve would hand B and C hidden text; with the rule the graph adds reach, not access. Concept text in C is the ontology layer under test. A controller ruling from the final review, open to the owner at CP1 part 2. | Retrieval, experiment, data |
| D-029 | 2026-10-19 | Controller ruling, approved by the project owner with CP1 part 3 on 2026-10-20: scipy is added for the Wilcoxon signed-rank test only (`scipy.stats.wilcoxon`, locked at 1.18.1 in `uv.lock`); the bootstrap, Holm correction and headlines are plain Python. | A tested signed-rank implementation with Pratt's zero handling is not worth rewriting; using it for one function keeps the rest of the statistics readable and dependency-free. | Evaluation, dependencies |
| D-030 | 2026-10-19 | Controller ruling, approved by the project owner with CP1 part 3 on 2026-10-20: bank 2.0.0 anchors. Each structural question samples up to three anchors per world in sha256 order of `bank version:question id:anchor`, among anchors inside fixed eligibility bounds (answer sets of 1 to 6 members once the anchor is excluded, with per-question bounds for L06, L11, L13 and L14). The anchor is excluded from claims, selected evidence and every set-check universe. An incident's markets are its own market, else its affected games' markets; incidents without a market of their own are never anchors of L05 or L10. L13 and L14 anchors are one per concept, spread across languages; L14 has exactly three qualifying concepts in seed 2026, so it has no margin. Planted (H5) questions take their truth from the ledger only. | Hashed sampling is stable and blind to retrieval; bounds keep answers checkable; excluding the anchor scores what a pipeline discovered rather than the id it was given; the ledger is the only evaluator source of planted truth (ADR-008). Open owner questions: L16 and L17 expected sets include baseline players, and L22 scores 0.5 when an answer also quotes the stale price. | Evaluation, experiment |
| D-031 | 2026-10-19 | Controller ruling, approved by the project owner with CP1 part 3 on 2026-10-20: the LLM judge (prompt 1.0.0) sees block text only, shuffled by a hashed seed and renumbered, with citation markers rewritten and other digit brackets shown as `[?]`; it must be of another model family than the generator in an official run; a judge failure is recorded and never scored as zero; judge scores never replace deterministic scores; agreement and kappa with the answer score are reported. | Blinding and the family rule limit self-preference and pipeline tells; recording failures keeps a flaky judge from biasing means. Known limitation: a graph node without a record block reads `<Label> <id>`, a residual tell. `judge_prompt_hash` covers the system prompt, its version and the user-message template. | Evaluation, model layer |
| D-032 | 2026-10-19 | Controller ruling, approved by the project owner with CP1 part 3 on 2026-10-20: the observation is one bank instance (mean over its successful repeats); pairs cluster by logical question and world (`question_id:world_seed`); the Wilcoxon test runs on per-cluster mean differences; the Holm family is evidence F1 on H1, H2 (by id) and H5 and answer on H1, H2, H3 and H5, for B against A and C against B; a claim needs at least 10 pairs and at least 6 clusters; the name-anchored H2 sub-group gets a descriptive interval with no test. | Instances of one question in one world are correlated, so the cluster is the independent unit for both the interval and the test; six clusters is the fewest at which a two-sided signed-rank test can reach p < 0.05. This changes the plan's instance-level test and gives fewer significant claims. | Evaluation, experiment |
| D-033 | 2026-10-20 | Proposed (controller ruling, for owner review at CP2): The run store is a SQLite file (`APP_DB_PATH`, default `data/app.db`) opened with WAL, one connection per thread, with every write in a `BEGIN IMMEDIATE` transaction so an event's sequence is assigned and stored in one step. Schema version 1 (`PRAGMA user_version`) has four tables: `runs`, `events`, `results` and `scores`, the last three deleted with their run; a database with a newer version is refused. It keeps the newest `RUN_RETENTION` finished live runs (default 500) and never prunes a queued or running run. At start-up every queued or running run is marked failed with `INTERRUPTED`, and every completed bank run without a score gets the interrupted score record. | Runs, events and scores must survive a restart and replay exactly as streamed (ADR-007). SQLite from the standard library is enough for one operator, and per-write transactions keep sequences gap-free under the worker and request threads. Marking interrupted runs at start-up means no run stays active or pending for good. | API, persistence |
| D-034 | 2026-10-20 | Proposed (controller ruling, for owner review at CP2): The event envelope has eight fields (`event_id`, `timestamp`, `run_id`, `pipeline`, `event_type`, `t_ms`, `payload`, `sequence`), identical in replay and in the stream. A worker brackets the pipelines' events with `run.started`, `pipeline.started`, `pipeline.completed`, `pipeline.failed`, `pipeline.cancelled` and one terminal event: `run.completed`, `run.failed` or `run.cancelled`. Cancellation is cooperative at event boundaries: a pipeline stops at its next emitted event. A cancel and a finish agree because the worker claims the run as finishing under one lock: a cancel accepted before the claim ends the run `cancelled`, one after it is refused with 409. The terminal event is stored before the final row, so a client that sees the final status finds every event. | One envelope and one terminal event let the frontend render live and replayed runs with the same code, and let a client stop reading at a known point. Cancelling only at event boundaries needs no thread interruption and loses no stored result; the single claim removes the race between a late cancel and a finishing run. | API, events, frontend |
| D-035 | 2026-10-20 | Proposed (controller ruling, for owner review at CP2): Only `app/api/benchmarks.py` and `app/api/scoring.py` may import `app.evaluation`, and a test enforces it (extending the truth-ledger isolation rule). A bank question run in Live Lab is scored after the run is complete with the benchmark runner's deterministic scorer (`score_pipeline_run`); no judge runs live and the score is labelled "scored against the answer key". A bank question runs with its own text and scope, so a live score equals the deterministic part of the benchmark's score. The scorer's message is never logged, because it can quote an expected value. | Scoring needs the answer key, so two modules must reach the evaluator; keeping that to two named modules keeps the isolation test meaningful. Scoring after the run, with the runner's own scorer, keeps retrieval blind to the key and makes live and benchmark scores comparable (spec 10a.1). | API, evaluation, truth-ledger isolation |
| D-036 | 2026-10-20 | Proposed (controller ruling, for owner review at CP2): The demo questions are the first bank instance, in bank order, of each of the strata H1, H2, H3 and H5, served by `GET /demo/questions` from the frozen bank of the presentation world (seed 2026). Before the bank is grounded the route is a 503 `CONFIGURATION_ERROR`, never an empty list. | The demo then asks questions the benchmark asks, scored by the same answer key, instead of hand-picked questions with no key; taking the first instance means no question is chosen to suit a pipeline. | API, UX, benchmark |
| D-037 | 2026-10-20 | Proposed (controller ruling, for owner review at CP2): Live runs and benchmark jobs share one Neo4j through a graph lease: any number of live runs, or one benchmark job, never both; each side is refused with a retryable 409 while the other holds the graph. Which world the graph holds is checked by comparing the live node count of every label with the active dataset's `_graph_stats.json`, cached for 30 s and not consulted while a job holds the lease. Equal counts are a fingerprint, not a proof. | A benchmark job re-ingests other worlds into the graph Live Lab reads, so live answers must never come from another world. A count fingerprint is one cheap statement and catches the real failure (a different world); a stronger proof would need a world id stored in the graph. | API, graph, benchmark |
| D-038 | 2026-10-20 | Proposed (controller ruling, for owner review at CP2): `GET /health/ready` runs four checks (`lab`, `index`, `graph`, `model`) concurrently, each under its own timeout, with curated details. The model check tests availability, not warmth: an Ollama model is available when the server lists it, any other provider must answer one 1-token call, and the result is cached for 30 s. The lab is built in a background thread at start-up; no route waits for it, a run started meanwhile waits for it, and readiness never builds it. | Readiness that loaded a cold model, or blocked on the lab build, could time out the very probe that tells an operator the server is starting. Warming at start-up moves the cold start out of the first run. | API, operations |
